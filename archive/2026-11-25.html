Judging coding agents gets harder as the targets move past ordinary code

Today's crop zeroes in on a problem that keeps resurfacing as coding agents mature: passing a test is not the same as doing the job right, and today's benchmarks mostly measure the former. SpecEngineeringBench makes this explicit by stripping away the usual scaffolding — no issue description, no designated test entry point, no pointer to which files matter — and asking seven frontier coding agents to act as autonomous specification engineers: translate functional requirements into their own test suites, then use those tests to hunt for real defects across 100 instances drawn from 78 open-source Python repositories. The results are sobering in a specific way: agents write valid, high-coverage tests (91% Head Pass Rate, over 80% change-focused coverage) but their actual defect-detection rate lags far behind at roughly 26%, and the ability to say precisely where a bug lives collapses from 78% recall at the file level to barely 51% at the function level. In other words, agents are good at looking busy and thorough while still missing the point.

AIChipBench pushes the same diagnosis into a domain where the stakes of "looks right but isn't" are even higher: having LLM coding agents implement quantized LLM decoders as synthesizable RTL hardware. Because a decoder carries state across steps, a design can pass every visible output test and still be silently wrong several tokens later — and indeed, when the authors regrade "accepted" designs on harder held-out sequences, 45 of 69 fail within just 32 steps. The fix that actually moves the needle isn't a smarter agent but better feedback: pointing agents at the first point where internal state diverges, rather than just the final output, lifts acceptance by 25 to 47 percentage points and halves the debugging effort, a strong argument that today's coding-agent harnesses are bottlenecked on what they're told about their own mistakes, not on raw capability.

Reading Decisions Before Spans attacks the adjacent cost problem: once you accept that verifying an agent's work requires a careful generative verifier rather than a cheap pass/fail check, that verification itself becomes expensive at scale. Studying over 2,000 code-agent test responses, the authors show that a verifier's real decision — is this claim supported or not — is settled at a single early branch point in its output, long before it generates the full quoted error spans that justify that call. By training the verifier to stop (or to be prompted to answer) right at that branch, they cut compute by as much as 85% relative to full-length generation while keeping the same F1 score, suggesting that the overhead of double-checking an agent's work can be slashed without weakening the check itself. Taken together, the day's papers sketch a consistent picture: as coding agents get judged on increasingly open-ended, state-aware, and expensive-to-verify tasks, the limiting factor isn't agent intelligence so much as the design of the feedback loop that tells them — and tells us — whether they actually finished the job.
